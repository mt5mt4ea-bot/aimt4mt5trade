# 技术栈与总体架构

## 1. 推荐生产技术栈

| 层 | 推荐 | 选择理由 |
|---|---|---|
| EA | MQL5，抽象兼容层后再适配 MQL4 | MT5 交易事件更完整；保留双平台空间 |
| API 网关 | Nginx/Traefik + FastAPI（Python 3.12+，锁定已验证版本） | 适合 JSON Schema、异步 I/O、AI/量化生态 |
| 分析服务 | Python、Pydantic、pandas/polars、TA-Lib 或 pandas-ta | 特征计算、严格输入输出校验 |
| 决策编排 | 确定性规则引擎 + 可插拔 LLM Provider | 数值和风险可测试，模型可切换/降级 |
| 任务队列 | Redis + Celery/Dramatiq | 隔离慢模型调用，支持超时与重试 |
| 数据库 | 受官方支持的 PostgreSQL 主版本 + TimescaleDB（可选） | 交易/审计关系数据与时序快照统一管理；按扩展兼容矩阵锁定版本 |
| 实时推送 | WebSocket/SSE；跨实例用 Redis Streams/PubSub | 面板低延迟更新 |
| 前端 | React 19.x + TypeScript + Vite；TanStack Query/Router | 实时控制台易模块化，类型安全；补丁版本由 lockfile 固定 |
| UI/图表 | Tailwind CSS + Radix UI；Lightweight Charts + ECharts | 无障碍控件、专业 K 线与分析图表 |
| 认证 | OIDC（Keycloak/Auth0/企业 IdP）+ RBAC；EA 用 HMAC/mTLS | 人员与机器身份分离 |
| 可观测性 | OpenTelemetry + Prometheus + Grafana + Loki/Sentry | 延迟、错误、交易事件全链路追踪 |
| 交付 | Docker Compose（开发）/ Kubernetes 或单区容器服务（生产） | 先简后繁，保留横向扩展 |
| CI/CD | GitHub Actions/GitLab CI，环境签名制品 | 自动测试、扫描、灰度与回滚 |

原型采用无依赖 HTML/CSS/JavaScript，便于立即评审；生产开发再迁移到 React 组件，不建议把原型代码直接接入实盘。

## 2. 服务拓扑

```text
MT5/MT4 Terminal
  └─ EA（采集 + 本地硬风控 + 唯一下单端）
       ├─ HTTPS/HMAC ─> API Gateway
       │                 ├─ Auth / Account Binding
       │                 ├─ Snapshot & Order Sync
       │                 ├─ Decision Orchestrator
       │                 │    ├─ Feature/Rule Engine
       │                 │    ├─ LLM Provider Adapter
       │                 │    └─ Server Risk Pre-check
       │                 ├─ Trade Plan Signer
       │                 └─ Audit/Event Service
       └─ Local SL/TP & Kill Switch

Web Console ── OIDC/HTTPS/WebSocket ──> API Gateway
                                      ├─ PostgreSQL/TimescaleDB
                                      ├─ Redis Queue/Stream
                                      └─ External Calendar/News Sources
```

## 3. 关键架构决策

### EA 是唯一下单端

浏览器和 AI 服务不保存交易主密码，也不直接调用交易商。后端返回签名计划，EA 按终端的实际报价和账户状态执行，使断线、滑点、最小止损距离和保证金等限制可以在离交易终端最近的位置处理。

### 交易计划而非自然语言指令

计划使用版本化 JSON Schema；后端用独立密钥签名，EA 验证后才解析。自然语言仅供解释，不能改变 `action/volume/SL/TP/expires_at`。

### 异步分析、短轮询取结果

MQL 的 WebRequest 会阻塞。EA 首次提交快照后获得 `202 + request_id`，通过 OnTimer 短轮询结果；服务端可在已有缓存结果时直接返回 200。若分析超过有效窗口，结果作废，不追单。

### 事件溯源与最终一致

订单全生命周期以事件追加保存，不覆盖历史。EA 是成交事实源，后端定期对账；前端显示“计划状态”和“交易商状态”并在不一致时告警。

## 4. 数据实体

- `account`：绑定账户、环境、币种、杠杆、权限。
- `ea_instance`：实例 ID、终端、版本、心跳、能力。
- `market_snapshot`：行情、多周期 K 线、指标、数据质量。
- `analysis_request`：请求状态、输入哈希、超时、错误码。
- `trade_plan`：动作、价格区间、风控、证据、签名、有效期、版本。
- `risk_check`：规则、阈值、观测值、通过/拒绝。
- `order_event`：提交、接受、部分成交、成交、改单、关闭、失败。
- `position_snapshot`：持仓、浮盈亏、SL/TP、管理状态。
- `audit_log`：人员/服务主体、操作、前后值、IP、追踪 ID。

所有实体均携带 `tenant_id/account_id`，服务端任何查询都必须按租户隔离。

## 5. 安全设计

- EA 首次绑定由管理员生成一次性注册码，换取 `key_id`；密钥仅保存在终端受限目录。
- 请求签名建议为 `HMAC-SHA256(method + path + timestamp + nonce + body_sha256)`；服务器允许时间偏差建议 ±30 秒并拒绝 nonce 重放。
- TradePlan 使用非对称签名更便于 EA 仅持有公钥验证；密钥轮换保留短期双公钥窗口。
- 管理员登录走 OIDC + MFA；修改风险上限、开启 AUTO、解除 HALTED、紧急平仓需 step-up authentication。
- 日志不得记录 API 密钥、完整 Token、交易主密码；账户号按权限掩码展示。
- 开发、模拟、实盘完全分离域名、数据库、凭据和发布通道。

## 6. 部署建议

### MVP/模拟盘

- Windows VPS：MT5 + EA。
- Linux 主机：API、worker、PostgreSQL、Redis，Docker Compose 部署。
- 独立静态前端或由 Nginx 托管。

### 实盘

- 至少 2 个 API 实例、托管 PostgreSQL、Redis 高可用、对象存储备份。
- EA 到 API 的网络延迟与可用性监控；数据库故障时禁止生成新计划。
- 发布采用模拟环境 → 影子模式 → 1 个灰度账户 → 分批账户；任何风险告警可自动回滚到 OBSERVE。

## 8. 技术选型的待确认项

- 如果团队以 TypeScript 为主，API 可用 NestJS，但量化/AI 分析仍建议独立 Python 服务。
- TimescaleDB 在 K 线量不大时可延后，首版使用普通 PostgreSQL 分区表。
- Kubernetes 不是 MVP 前置条件；单账户/低并发先用 Compose，验证稳定性后再扩展。
- LLM 供应商通过统一适配器接入，不能让业务协议绑定某个模型厂商。

## 9. 官方技术依据（校验于 2026-09-13）

- [MQL5 WebRequest](https://www.mql5.com/en/docs/network/webrequest)：同步阻塞、EA/脚本调用限制、允许 URL 配置以及 Strategy Tester 不可用说明。
- [MQL5 OnTradeTransaction](https://www.mql5.com/en/docs/event_handlers/ontradetransaction)：一个请求可能产生多个事件、事件顺序不保证、处理队列限制。
- [React Versions](https://react.dev/versions)：React 19 当前主版本；生产依赖仍通过 lockfile 固定到已测试补丁版本。
- [FastAPI Versioning](https://fastapi.tiangolo.com/deployment/versions/)：官方建议对已验证版本进行 pin，避免快速迭代带来的不兼容。
- [PostgreSQL Versioning Policy](https://www.postgresql.org/support/versioning/)：每个主版本支持 5 年；新项目选择仍需同时核对 TimescaleDB 等扩展兼容性。
